## 1. 학교 환경 현황

- **디지털 도구 이중 체계**: 구글 워크스페이스 + 마이크로소프트 팀즈를 동시 운영 중
  - 교사 계정: 구글·팀즈 모두 사용
  - 학생 계정: 공식적으로는 팀즈만 사용, 일부 교사가 개별적으로 학생용 구글 계정을 만들어 사용 중 (비공식)
  - → 스마트교무실은 구글 OAuth 기반 로그인이 전제이므로, 학생 로그인 체계를 그대로 적용하기 어려운 지점. 도입 시 별도 검토 필요.
- **자체 개발 역량 보유**: 정보부장 교사가 바이브 코딩(AI 활용 개발)으로 자체 서비스를 개발·운영 중
- 그 외에도 다양한 디지털 도구를 병행 사용 중 (구체 목록은 미확인)

## 2. 학교가 의뢰한 문제

- 교육 프로그램 참여 기록 서비스, 생기부 보조 서비스, 고사(시험) 서비스 등 여러 개별 서비스를 이미 적극 활용 중
- 문제는 **통합 부재**: 각 서비스가 독립된 구조로 작동하여 학생 정보가 도구 간에 연결되지 않고, 일괄 관리가 안 됨
- 즉, "새 도구가 필요하다"보다는 "이미 있는 도구들을 하나의 데이터 기반으로 묶고 싶다"는 니즈에 가까움

## 3. 현장 논의 내용 정리

### 3-1. 개발 진행 방식과 데이터 통합의 어려움
- 이대부고도 자체적으로 데이터 통합을 시도하고 있으나,애초에 **통합을 전제로 설계된 구조가 아니어서** 시간이 오래 걸릴 것으로 예상됨
- 스마트교무실의 개발 과정(설계 철학, 진행 방식)을 소개하고 질의응답 진행
- 정보부장 교사가 본인의 개발 현황을 공유

### 3-2. 통합 DB 구조에 대한 공감대
- **학생 계정과 교사 계정을 중심축으로 삼아 통합 DB 구조로 발전시키는 방향**에 대해 양측 모두 공감
- (스마트교무실의 `/schools/{schoolId}/teachers`, `/students` 구조와 방향성이 유사 — 참고 자료 참조)

### 3-3. 1인 개발의 한계와 협업 구조 고민
- 이대부고 정보부장 교사가 **개인 단독 개발의 한계**를 토로함
- 바이브 코딩 환경에서의 **협업 방식**에 대한 고민 제기
- **확인 필요 사항**: GitHub를 활용해 여러 명이 함께 작업할 수 있는 프로젝트 구조 설계가 가능한지 추후 확인 필요 (액션 아이템)

### 3-4. 보건실 출입 관리 시스템 아이디어
- 학교 보건실 앞에 남는 태블릿을 활용한 **키오스크형 출입 관리 시스템** 구상 논의
- 개발 자체의 기술적 난이도는 낮다고 판단됨
- 다만 **개인정보(건강정보) 저장·관리에 대한 우려**가 컨설팅 현장에서 제기됨 — 민감정보 처리 방식(보관 기간, 접근 권한 등)에 대한 별도 검토 필요

### 3-5. AI/바이브 코딩 비용 구조에 대한 의견
- 학교 내 AI 활용(바이브 코딩 등) 확산 시 **API 사용량 과다에 따른 비용 문제** 지적
- 개인별 구독 서비스(예: 개별 유료 플랜) 방식보다, **학교 차원에서 별도 계정을 하나 만들고 그 계정으로 API 비용을 선결재(예산 편성)하는 방식**이 더 합리적이라는 의견 제시
  - 이유: 구독형은 사용량과 무관하게 고정 비용이 나가고 개인별로 중복 계약될 수 있는 반면, 학교 단위 API 계정은 실사용량 기반으로 통합 관리 가능

## 4. 후속 질의응답 — 기술 검토 (2026-07-08)

컨설팅 현장 논의(3-2, 3-3)를 바탕으로, 실제 스마트교무실 코드베이스를 확인하여 아래 두 질문에 대한 답을 정리함.

### Q1. schoolId 기반 구조에서 다양한 서비스로 데이터 연결이 가능한가? 작업량은? 향후 서비스 확장에 용이한 구조로 바꿀 수 있는가?

**현재 구조 (코드 확인 결과)**
- 모든 모듈(출결·보강·연수·공지)이 `/schools/{schoolId}/모듈명/...` 경로를 공유하는 단일 패턴으로 되어 있음
- `schoolId`는 `/users/{uid}.schoolId` 필드가 단일 소스(source of truth)이며, 모든 모듈이 공통 `AuthContext`에서 이 값을 가져다 씀
- `firestore.rules`도 `isTeacher(schoolId)` / `isStudent(schoolId)` / `isSchoolAdmin(schoolId)` 공통 헬퍼 함수로 전 모듈의 접근 제어를 통일 — 이미 4개 모듈에서 검증된 재사용 패턴
- (참고) `PLAN_multiSchool.md`(4월 작성, "미착수" 표기)에는 "로그인 시 도메인으로 학교 자동 배정" 설계가 있었으나, 실제 구현은 그와 다르게 "도메인으로 학교 추천 → 수동 가입 신청 → 관리자 승인" 방식으로 되어 있음. 문서가 최신 코드를 반영하지 못한 상태.

**답변 — 시나리오를 나눠서 봐야 함**

| 시나리오 | 내용 | 작업량/난이도 |
|---|---|---|
| A. 스마트교무실 안에 새 모듈로 구현 | 참여기록·고사 관리 등을 이 코드베이스 안에 신규 서비스로 추가 | 인증·권한·학교분리는 기존 패턴 재사용 가능. 프레임 구축만 놓고 보면 수일~1~2주 규모 |
| ~~B. 이대부고 기존 독립 서비스를 API/마이그레이션으로 연동~~ | (검토 후 기각) 각 서비스가 별도 시스템/DB이고 API 존재 여부·스택이 불명확해 현실성 낮음 | — |

> **방향 수정(2026-07-08 논의)**: 기존에 흩어져 있는 이대부고 서비스들을 API/마이그레이션으로 억지로 이어붙이는 것은 현실성이 떨어진다고 판단함. 대신 **정보부장 선생님이 처음부터 통합을 염두에 둔 구조로 전체 서비스를 재설계·개발할 수 있도록, 스마트교무실의 DB 구조(schoolId 파티션 + 공통 인증/권한 패턴)를 참고 모델로 공유하고 자문하는 방향**이 더 현실적. 이 경우 스마트교무실 쪽 "작업량"이 아니라, 이대부고 쪽이 참고할 **설계 가이드/컨설팅**의 형태가 됨 (§5 참고).

**추가로 걸리는 지점**: 스마트교무실 학생 인증은 구글 OAuth + 이메일 로컬파트 9자리 숫자 패턴에 의존함. 이대부고는 학생 계정이 팀즈 중심(§1 참고)이라, 데이터 스키마보다 오히려 **이 로그인 전제 조건이 실제로는 더 큰 도입 장벽**일 가능성이 큼. 정보부장님이 자체 설계할 경우에도 이 부분(학생 식별 방식)은 이대부고 환경(팀즈)에 맞게 별도로 정해야 함.

### Q2. GitHub 협업 방식 — 순차적(push→pull→이어작업)만 가능한가? 2명이 동시 작업은 불가능한가?

**답변**: 동시 작업 가능함. "같은 파일의 같은 줄"만 아니면 두 사람이 동시에 수정 가능 — Git은 파일을 잠그지 않고 변경 내역(diff)을 병합하는 방식이기 때문.

- **권장 구조**: 각자 작업 전 `main`에서 별도 브랜치(예: `feature/보건실-출입`)를 파서 작업 → 물리적으로 격리되어 충돌 위험 감소 → 완료 후 Pull Request로 `main`에 병합
- 브랜치가 다르면 동시에 커밋·push해도 문제없음. 충돌은 병합 시점에만 발생하며 대부분 Git이 자동 처리, 안 되는 부분만 사람이 정리
- **바이브 코딩 특유 리스크**: AI가 파일을 광범위하게 재작성하는 경향이 있어, 두 사람이 각자 AI에게 "전체적으로 손봐줘" 식으로 맡기면 같은 파일이 크게 달라져 자동 병합이 어려워질 수 있음 → 작업 단위를 기능/모듈 단위로 명확히 쪼개고 브랜치를 짧게 유지·자주 병합하는 것이 특히 중요
- 결론: 실시간 동시 편집(Google Docs 방식)은 아니지만, 브랜치로 격리한 비동기적 병합 협업으로 2인 이상 동시 개발이 가능함

## 5. 이대부고 대응 방향 정리 (2026-07-08 논의)

Q1 검토 결과 기존 서비스 API/마이그레이션 연동은 현실성이 낮다고 판단, 아래 방향으로 정리함.

1. **DB 구조 자문 제공**: 스마트교무실의 `/schools/{schoolId}/...` 파티션 구조 + 공통 인증/권한 패턴(모든 모듈이 `schoolId`·`role`을 공유하는 방식)을 참고 모델로 정보부장 선생님께 공유. 이대부고가 앞으로 개발할 서비스들(참여기록, 생기부보조, 고사 서비스 등)을 **처음부터 통합을 염두에 둔 구조로 직접 설계·개발**할 수 있도록 돕는 방향.
2. **협업 개발 구조 논의**: 1인 개발의 한계(§3-3)를 해소할 수 있도록, GitHub 기반 브랜치·PR 협업 구조(§3-3, Q2)를 이대부고 개발 환경에 어떻게 적용할지 실무적으로 논의.
3. **스마트교무실 공동 개발 참여 제안**: 정보부장 선생님을 스마트교무실 개발에 **협업 멤버로 초청**하는 방안도 검토 중. 실제 다학교 협업 개발 사례를 만들어보면서 위 1·2번 논의를 실전으로 검증할 수 있는 기회가 될 수 있음.

- [ ] 정보부장 선생님께 스마트교무실 GitHub 저장소 협업 멤버 초청 제안 여부 및 시점 결정
- [ ] 초청 시 권한 범위(어느 모듈까지 접근 허용할지), 브랜치 전략 등 실무 규칙 사전 정리
- [ ] 이대부고 학생 계정(팀즈 중심) 환경에 맞는 학생 식별 방식 별도 설계 필요성 안내
- [ ] 보건실 출입 시스템의 개인정보(건강정보) 처리 방안 — 법적 근거, 보관기간, 접근권한 설계 필요 (§3-4)
- [ ] 학교 단위 AI API 계정 선결재 구조의 실제 적용 사례 또는 예산 편성 방식 조사 (§3-5)
